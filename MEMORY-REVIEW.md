# Construction memory review

This updates PR #21 without changing the production table design. The full [Wago memory review](https://github.com/wago-org/wago/blob/perf/setup-cleanup-measured/docs/performance/setup-cleanup/memory-review/README.md) contains source/binary hashes, exact commands, paired raw data, confidence intervals, profiles and script corrections. Wago's dependency pin is unchanged.

The reviewed provider head was `a6169cc6ebf86b5d2a98bd009e672dac02be1542`, with PR base `aef440ccb4368b87f122038cf31295bba1b4bd46`. The historical performance experiment instead used base `6a6684d2ecd2be2d17e5792733d1d0e03b2f2c0e`. Both bases have identical core.go production content; they were built and recorded separately. Current comparisons use the snapshot-fixed Wago source in both provider builds and change only the provider production patch. A separate snapshot comparison fixes the provider revision.

The table saves 70 allocations and 11,392 allocated bytes per raw WASI construction. A reused provider saves this once at registration, not on every instance. Package initialization adds 4,992 allocated bytes and 24 allocations once per process. The live heap profile after completed cleanup and GC retains only that fixed definition allocation from this provider. The table contains no per-registration Plugin, caller, configuration, stream or descriptor owner.

For 1,000 tinyxml2 raw commands, current-base normal HeapAlloc increased by a paired mean 925,945 B (20 pairs, 95% interval 696,569–1,175,127 B), while GC cycles fell from a median 13 to 9. After GC the heap difference was only 993 B (−951 to 2,803 B). This supports different GC phase and uncollected dead objects as the principal cause of the large normal heap endpoint. Lower allocation volume does not prove lower live memory or RSS.

The old endpoint called released-gc actually used debug.FreeOSMemory (GC plus scavenging). The historical +756 KiB tinyxml2 RSS result is present in the saved rows. A new current-base session found +799.4 KiB (232.2–1,340.0), but its preselected separate 20-pair confirmation found +234.4 KiB (−350.8 to 824.0). Detailed mappings place most of the first increase in anonymous writable pages, not live provider objects or growing code images. The exact residual RSS mechanism remains unresolved. The ~5 KiB table does not explain ~756 KiB by itself. No production memory fix is justified by this evidence.

Direct single host-call time was unchanged in the table comparison, but the 1,024-call control slowed 1.26%, and a separate fixed 20-pair confirmation slowed 1.75%. An isolated private-argument candidate improved heavy calls but repeatedly worsened the single-call control (~1%); it was rejected and never entered this branch. The small original heavy-host-call regression remains open. The construction gains do not conceal this tradeoff.

The new `TestConstructionCleanupDropsInstanceState` checks empty instance-state maps after each of 400 commands which leave a guest-opened file for cleanup. Runtime close must drop initial provider state and preserve borrowed streams. Existing tests cover normal exit, guest/start traps, denied instantiation, cancellation, partial setup, repeated close, metadata/config mutation and cross-instance cleanup isolation. Raw-import and registered-provider cleanup contracts remain distinct; this change does not claim that Instance.Close closes raw WASI resources.

Local full provider race tests and vet passed on Go 1.22.12 and Go 1.27.1 on Linux amd64. The Go 1.22-compatible closed-descriptor test remains intact. CI passed all 14 checks on the new test commit `d6870db`, including ARM64 and Go 1.22. Wago's new 72-case execution allocation screen remains at zero B/op and zero allocs/op. No new all-engine 984-case timing run or local ARM64 execution was performed. Final documentation-head CI status is recorded in the PR update.

Status: lifecycle regression coverage **implemented and verified**; memory diagnosis **completed with no accepted production memory change**; precise RSS attribution and a safe heavy-host-call improvement remain unresolved.
